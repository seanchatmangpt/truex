# Tutorial 2: Deterministic Replay

One of Truex's most powerful and distinguishing features is Deterministic Replay. It allows developers and operators to exactly reproduce the execution of any capability, making debugging complex state transitions, race conditions, and transient failures trivial.

## Theoretical Context

To fully leverage Deterministic Replay, it helps to recall the core Truex architecture:

1. **Gall Sequencing**: Deterministic replay relies entirely on the strict, immutable event log generated by the Gall sequencer. Every input, state mutation, RNG seed, and side effect is recorded with a cryptographic hash, creating a perfect timeline.
2. **OTP Equivalence**: Because our hooks are modeled as isolated, message-passing processes (supervision tree equivalence), replaying a single hook's lifecycle without affecting the rest of the system is mathematically sound and safe.
3. **Operational Topology**: Replay uses the Operational Topology to effectively mock downstream capability dependencies. By understanding the graph, the replay engine ensures that replayed nodes don't trigger real-world side effects (like sending emails or charging credit cards).

## Step 1: Capturing Execution Receipts

To replay an execution, you first need an execution receipt. In the previous tutorial, we saw how the `execute` method returns a receipt object. In a production system, these are typically shipped to a database or blob storage.

```typescript
import { GallSequencer } from '@truex/core';
import fs from 'fs';

// Assume processOrderHook and initialState are imported/defined
async function captureReceipt() {
  const sequencer = new GallSequencer();
  const receipt = await sequencer.execute(processOrderHook, initialState);

  // Save this receipt to a file for later replay analysis
  fs.writeFileSync('receipt.json', JSON.stringify(receipt, null, 2));
  console.log(`Receipt saved: ${receipt.hash}`);
}
```

## Step 2: Setting up the Replay Engine

Now, let's load the receipt and configure the `ReplayEngine`.

```typescript
import { ReplayEngine } from '@truex/core';
import fs from 'fs';

const receiptData = JSON.parse(fs.readFileSync('receipt.json', 'utf8'));

// Initialize the engine in isolated mode
const engine = new ReplayEngine({
  topologyMode: 'isolated', // Crucial: ensures we don't trigger real side effects
  strictValidation: true    // Verify hashes at each step
});
```

## Step 3: Executing the Replay

You can run the replay engine programmatically. In more advanced use cases, you might attach a debugger or use a step-through interface to pause execution at specific Gall sequence indices.

```typescript
async function replayExecution() {
  console.log(`Replaying execution for hash: ${receiptData.hash}`);
  
  const replayResult = await engine.replay(receiptData);
  
  // Verify that the replay outcome perfectly matches the historical execution
  if (replayResult.matches) {
    console.log('✅ Replay successful and matches original execution perfectly.');
  } else {
    console.error('❌ Replay divergence detected!');
    console.error('Original Output Hash:', receiptData.outputHash);
    console.error('Replay Output Hash:', replayResult.outputHash);
  }
}

replayExecution();
```

## Troubleshooting Divergence

If `replayResult.matches` is false, it means your hook execution is non-deterministic. The replay engine will pinpoint the exact sequence step where the hashes diverged.

Common causes of divergence:
1. **Relying on `Date.now()`**: Using native system time breaks determinism. Always use `ctx.time.now()` instead, which is deterministic during replay (it pulls the timestamp from the receipt).
2. **Math.random()**: Similar to time, native randomness is problematic. Use `ctx.random.next()` to utilize the framework's seeded pseudo-random number generator.
3. **External Network Calls**: If your hook makes raw HTTP calls (e.g., via `fetch`), the responses will vary. You must wrap network calls using Truex's boundary/membrane system, so the responses are captured in the receipt and mocked during replay.

## Exploring the Topology During Replay

During a replay, the Operational Topology acts as a read-only historical map. You can ask the replay engine what the topology looked like at that exact moment in the past.

```typescript
const historicalTopology = engine.getTopologyAtReplayTime();
console.log('Historical nodes active during execution:', historicalTopology.getNodes());
```
