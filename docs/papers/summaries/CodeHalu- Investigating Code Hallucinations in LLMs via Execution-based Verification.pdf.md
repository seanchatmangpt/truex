# Summary: CodeHalu: Investigating Code Hallucinations in LLMs

**File:** CodeHalu- Investigating Code Hallucinations in LLMs via Execution-based Verification.pdf

## 1. Main Thesis
Code hallucination is the phenomenon where code generated by LLMs is syntactically correct and semantically plausible but ultimately fails to execute correctly or meet requirements. The paper proposes a systematic classification and a dynamic detection algorithm (CodeHalu) to quantify these failures via execution-based verification.

## 2. Key Findings
- **Hallucination Taxonomy:** Hallucinations are categorized into four types:
    1. **Mapping:** Misunderstanding data types/structures (e.g., accessing non-existent keys).
    2. **Naming:** memory-related inaccuracies (e.g., undefined variables).
    3. **Resource:** Lack of perception regarding physical constraints (e.g., memory overflow).
    4. **Logic:** Discrepancies between expected results and actual outcomes (e.g., logic breakdown).
- **Execution as Ground Truth:** Unlike NLP hallucinations, code hallucinations must be verified through actual execution and test cases, as the "value" of code is realized only through successful performance.
- **Code Errors vs. Hallucinations:** Code errors are a proper subset of hallucinations. A "SyntaxError" may be the visible symptom of a "Logic Breakdown" hallucination.
- **HR Metric:** The study introduces the **Hallucination Rate (HR)**, the first metric that accurately reflects the frequency of these latent failures across different models.

## 3. Truex Grammar of Consequence Analysis

### Substrate (The Execution Environment)
The "Code Generation Instruction" and "Problem Description" define the initial state of the substrate.

### Membrane (The CodeHalu Algorithm)
CodeHalu acts as an **Active Computational Membrane** that intercepts generated code. It does not look at the code's "words" (Syntax) but at its "behavior" (Execution).

### Attempt (The Model-Generated Solution)
The code solution generated by an LLM is a raw **Attempt** to mutate the system state to satisfy a requirement.

### Admit / Refuse (Execution Verification)
Transitions are **Admitted** only if they pass all test cases $t_n$ without "Stuttering" or "Logic Collapse." They are **Refused** (and recorded in the hallucination set $\xi$) if they trigger runtime errors or produce incorrect $ER_{actual}$ values.

### Receipt (The CodeHaluEval Record)
The final "Receipt" is the **Hallucination Rate (HR)** report, documenting the exact failure mode (Mapping, Naming, etc.) for each attempt.
