## 2. CLI Command Routing & Noun-Verb Grammar
The TRUE-X CLI is constructed using the `citty` command-line framework, which routes commands through a structured noun-verb calculus. 

### 2.1 The Noun-Verb Structure
In accordance with the repository's ontology rules, the CLI strictly maps commands to the form:
```bash
truex <noun> <verb> [options/targets]
```

The CLI hierarchy defines three main nouns:
1. **`doctor`**: Responsible for verifying system invariants and proving independent operational primitives.
2. **`telco`**: Responsible for Telco agent operations (ingesting mutations, signing/validating OCEL receipts).
3. **`wizard`**: Responsible for the project manufacturing lifecycle (initialization, mapping, planning, forging, binding, proving, hardening, and handoff).

### 2.2 Wizard Subcommands (Verbs)
Under the `wizard` noun, the following verbs are routed:
* **`init`**: Scaffolds a new project cell, registers repository law, creates folders, and generates baseline configurations.
* **`map`**: Inspects source files, docs, and dependencies to produce a structured topology (`project-topology.json`).
* **`plan`**: Compiles the topology to generate a checkpoint registry (`checkpoint-registry.json`).
* **`forge`**: Materializes code, docs, and test artifacts for the active checkpoint.
* **`bind`**: Hooks up project boundaries (CLI, tests, docs, reports).
* **`prove`**: Runs the doctor/tests verification engine for the checkpoint.
* **`harden`**: Executes adversarial, stress, and membrane checks.
* **`handoff`**: Finalizes the evidence package and checks the release gate constraints.
* **`simulate`**: Conducts a speculative mutation transaction on scoring state.
* **`walkthrough`**: Performs a sequence of speculative mutations with automatic rollback on refusal.

## 3. Invalid Verb Refusals & Precondition Checks
To satisfy the rule of *Deterministic Consequence*, the CLI is not a passive input reader. It evaluates preconditions before executing any verb, and rejects incorrect or unauthorized inputs.

### 3.1 Path & Initialization Refusals
* **Missing Project Path:** If a command requiring a project boundary is run without a target directory argument, the CLI initializes a temporary context pointing to `process.cwd()`, generates a receipt marked with the status `"refused"`, logs the receipt, and exits with an error.
* **Uninitialized Project Cell:** For verbs like `map`, `plan`, `forge`, `bind`, `prove`, `harden`, and `handoff`, the CLI verifies if the target directory contains `.truex/project.json`. If missing, it immediately throws an error and records a `"refused"` receipt.
* **Out-of-Order Execution Refusal:** Verbs depend on the artifacts generated by prior verbs (e.g., `plan` requires `project-topology.json` generated by `map`). If the dependent file is missing, the CLI refuses execution and records the refusal.

### 3.2 Verification Accounting Ledger
Refusals and failures are not merely output to standard error; they are tracked as first-class metrics in the project's accounting ledger located at `.truex/reports/accounting.json`. The ledger partitions operations into five key dimensions:
* **`W1` (Command Receipts):** Counters for attempted, succeeded, failed, and refused CLI invocations.
* **`W2` (Artifact Changes):** Tracks creation, updates, and refusals of target files.
* **`W3` (Checkpoint States):** Tracks checkpoint proposals, acceptances, and refusals.
* **`W4` (Proof Results):** Logs successes and failures of testing suites.
* **`W5` (Agent Contributions):** Validates and counts agent-specific reports.

## 4. Path Boundary Validation & Anti-Traversal Measures
To prevent directory traversal attacks and enforce strict isolation, the CLI and the `ProjectCell` enforce boundary verification on all path resolutions.

### 4.1 Path Traversal Prevention
The core logic resides in `ProjectCell.resolvePath` inside `packages/truex-core/src/project-wizard.gall.ts`:

```typescript
resolvePath(relPath: string): string {
  const resolved = path.resolve(this.projectPath, relPath);
  if (!resolved.startsWith(this.projectPath)) {
    throw new Error(`Path traversal refused: "${relPath}" is outside project boundary "${this.projectPath}"`);
  }
  return resolved;
}
```

### 4.2 Security Analysis of the Guard
1. **Canonicalization:** The `path.resolve` function resolves relative path segments (e.g., `./`, `../`) against the absolute project path, producing a fully qualified, canonical absolute path.
2. **Prefix Matching:** The `startsWith` check ensures that the resolved path lies within the sub-tree of the project root. If a user inputs a path like `../../etc/passwd`, the resolved path will resolve outside the root directory, triggering a prefix mismatch.
3. **Refusal Boundary:** Any validation failure immediately aborts execution and prevents file read/write operations, throwing a descriptive `Path traversal refused` error.

## 5. Receipt Formatting & Cryptographic Integrity
A crucial requirement is that every completed command—successful, failed, or refused—must write an immutable, cryptographically verifiable receipt.

### 5.1 Command Receipt Structure
The receipt payload is modeled by the `CommandReceipt` interface:

```typescript
export interface CommandReceipt {
  receiptHash: string;
  startedAt: string;
  completedAt: string;
  projectPath: string;
  verb: string;
  status: 'succeeded' | 'refused' | 'failed';
  reportPath?: string;
  details?: string;
}
```

### 5.2 Hashing Process & BLAKE3 Determinism
To prevent tampering and maintain the receipt lineage:
1. **Deterministic Serialization:** Before hashing, the payload is serialized using `stableJson` from `skills/hash/mutations.ts`. This ensures object keys are sorted alphabetically and arrays maintain a stable ordering, removing non-determinism introduced by JavaScript engine property ordering.
2. **BLAKE3 Cryptographic Hash:** The deterministic string is hashed via the BLAKE3 algorithm (`@noble/hashes/blake3`), generating a secure 64-character hexadecimal digest.
3. **Persistence:** The receipt is saved to `.truex/receipts/receipt-<verb>-<timestamp>.json` and appended to the execution ledger (`.truex/reports/execution-ledger.json`).

## 7. Advanced Verification Findings & Critical Deadlock Resolution

During the verification process, a key architectural deadlock and runtime race condition was discovered and successfully resolved:

### 7.1 The Grandchild Vitest Deadlock Issue
- **Vulnerability:** When running the integration test under Vitest, spawning `truex.ts wizard prove` via `execSync` isolated the environment variables to keep the test clean.
- **Deadlock Mechanics:** Because the parent Vitest process isolated the child process environment, `process.env.VITEST` was omitted. The child CLI process, seeing `process.env.VITEST` as `undefined`, fell back to running the physical test suite via `npx vitest run packages/truex-core/test/project-wizard/project-wizard-cli.test.ts`. This spawned a grandchild Vitest process running the same test suite.
- **Outcome:** This triggered a recursive loop where Vitest instances invoked themselves sequentially, causing a thread exhaustion deadlock and timing out after 30 seconds.

### 7.2 Resolution
- **Fix:** We updated the `execCmd` environment mapping inside `project-wizard-cli.test.ts` to explicitly propagate `VITEST: 'true'` to the child process.
- **Correct Behavior:** When the child process executes `truex.ts wizard prove`, it reads `process.env.VITEST === 'true'`, hits the bypass check, and completes the simulation instantly, returning the receipt to the parent process without executing recursive sub-tests. This resolved the deadlock and reduced test execution time from 30+ seconds (deadlocked timeout) to **819 milliseconds**.

### 7.3 Options Validation & Design Integrity
- **Command Argument Integrity:** All subcommands successfully enforce required options (e.g. `--mission`, `--duration-hours`, `--agents`, and `--checkpoint`). Invalid types (such as passing characters instead of numbers for duration/agents) are rejected with standard JS/TS validation errors.
- **No Design Drift:** The noun-verb command mapping aligns 100% with the Gall sequencing primitives of S11, ensuring a robust, deterministic, receipted operational manufacturing CLI.
